# 写设计文档

## 文件组织

- 每份设计使用独立目录：`docs/designs/<序号>-<主题>/design.md`。
- 新建时检查已有编号，使用最大编号加一，至少两位补零，例如 `01-remote-plugin`、`02-connection-layer`。索引文件不参与编号。更新已有设计沿用原目录，不重新编号。
- 主题使用简短、可读的目录名，优先沿用项目已有命名习惯。
- 与本设计有关的附录、图示、HTML、示例配置、数据文件和其他附件，全部放在该设计目录内；必要时使用其下的 `assets/`、`appendices/` 等子目录。不把本设计附件散放在其他设计目录或公共目录。
- 附件使用相对链接引用，保证移动整个设计目录时附件关联仍然完整。已有源码、通用项目文档和外部参考网页可直接链接，不必复制；为本设计新增或导出的外部文件必须归档在本设计目录内。
- 更新 `docs/designs/README.md` 的设计索引；缺少索引时创建。移动或重命名文档时更新现有引用。

## 文档元信息

在标题之后放置由 `---` 包围的元信息区块，每份文档必须包含以下键：

```text
---
创建时间: 2026-10-12T13:30:00+08:00
Base commit: <完整 commit SHA>
最后修改时间: 2026-10-12T13:30:00+08:00
创建人: <git username>
---
```

这些键分别遵循以下获取与维护规则：

- 创建时间：创建时的实际时间，包含时区；更新时保持原值。
- Base commit：创建时使用 `git rev-parse HEAD` 获取完整 SHA；更新时默认保持原值，只有明确重新设定设计基线时才修改并说明。
- 最后修改时间：本次内容修改的实际时间，包含时区；首次创建时与创建时间相同。
- 创建人：默认使用目标仓库的 `git config user.name`；用户指定创建人时使用指定值，更新时保持原值。

从实际仓库和系统时间读取这些值，不用 GitHub 用户名替代 Git username，也不根据聊天日期猜测时间。Git 用户名缺失时向用户询问或明确标注待填写，不修改 Git 配置。非 Git 仓库或基线不可取得时如实记录原因，不虚构 SHA。

若工作区有未提交的设计相关代码，说明设计依据包含工作区内容；Base commit 仍记录 HEAD，不将未提交状态伪装为该 commit 的实现。

为旧文档补元信息时，先查 Git 历史等可用证据。无法确认的创建时间、创建人或原始基线标注未知，不把本次编辑时间冒充历史创建时间。

## 内容选择

先根据需求与当前代码写清问题、目标、最终建议和实现边界。明确区分当前实现、拟议设计与后续扩展，避免把讨论中的方案写成已上线能力。

复杂设计通常覆盖以下内容，按读者理解顺序组织，不限定章节名或顺序：

- 设计目标：要解决的问题、预期行为和适用范围。
- 总体架构：主要组件、依赖关系、关键数据或调用流程。
- 职责边界：状态归属、资源所有权、接口契约以及组件之间的责任。
- 实现方案：主要方案、必要的替代方案、取舍、生命周期与失败路径。
- 修改范围：相关模块、文件、API、协议、配置与迁移兼容影响。
- 性能影响：热路径、分配、拷贝、队列、并发或资源成本；区分实测、目标和待验证判断。
- 测试设计：关键行为、失败和并发场景、兼容性验证，以及必要的性能验收方法。

可按需要增加风险、部署、分阶段实施、待决问题和参考资料。简单需求或不适用的需求允许自由结构，用简短段落说明方案即可；不要为凑齐模板写空章节或重复内容。目录归档和元信息要求仍适用。

用户只要求写设计时，完成文档及必要附件、索引，不自动实施设计中的代码改动。没有证据的性能数据不写成结论。

## 完成检查

- 确认编号唯一、正文为 `design.md`，本设计新增附件均在同一设计目录内。
- 确认四项元信息存在，更新时保留创建信息与基线。
- 检查索引、源码引用和附件相对链接是否指向真实目标。
- 使用 `git diff --check` 检查本次文本修改，保留与任务无关的工作区内容。
- 交付时给出设计文档链接，简述关键决策和仍需用户决定的问题。
