# Voce Development Guidelines

This file defines the default way to develop, refactor, debug, and review code in this repository. It is not an attempt to impose a conventional enterprise layering scheme. The goal is to keep boundaries explicit and prevent runtime and memory-model regressions while preserving iteration speed on a real-time system.

## 1. Project positioning

Voce is a DAG runtime and plugin orchestration project for real-time voice interaction. The current focus is the voice path:

- ASR -> LLM -> TTS
- Interruption, streaming output, concurrent sessions
- Low latency, low allocation, stable tail latency
- Standalone mode, Gateway cluster mode, and cross-language Remote Plugins (the latter two are experimental)

It is a real-time runtime first, and an HTTP service, visual editor, and client collection second. Every change should respect that ordering. Do not sacrifice real-time behavior, interruptibility, or buffer reuse for local code tidiness. See `docs/overview.md` for the capability overview.

## 2. Repository layout

Full directory documentation lives in `README.md`; the documentation structure is defined in `docs/README.md`. This section only covers where code belongs, so it is not duplicated in prose.

| Directory | Contents | Notes |

| `internal/gateway`, `internal/machine` | Gateway control plane and machine data plane | Experimental; must not host plugin execution semantics |

Before adding a directory, check that it does not duplicate a responsibility listed above. If it is only an implementation detail of a package, keep it inside that package.

## 3. Architectural boundaries

### 3.1 engine is the single local DAG runtime core

- DAG scheduling, node wiring, session lifecycle, multi-track execution, backpressure, and interruption semantics all live in `internal/engine`.
- Do not reimplement runtime mechanics in `biz`, `clients`, or individual plugins.
- If a behavior affects plugin scheduling, context cancellation, queueing, or consumer dispatch, consider whether it belongs in `engine` before stuffing it into a plugin.

### 3.2 schema is the single data-carrier abstraction

- `Payload`, `Audio`, `Video`, and `Signal` are the only data forms exchanged at runtime.
- Do not introduce side-channel data structures that bypass `schema`.
- Any extension to `schema` must account for:
  - read-only / mutable transitions
  - reference counting
  - buffer reuse
  - concurrent fan-out reads

### 3.3 Plugins are an integration layer, not a second runtime

- Plugins integrate external models, services, and local processing.
- Plugin-local state is fine, but it must serve that plugin's processing needs. It must not become a cross-plugin orchestration hub.
- When logic repeats across multiple plugins, prefer:
  - shared plugin capabilities under `internal/plugins/base`
  - or a lower-level, stable abstraction in `internal/engine` / `internal/schema`

### 3.4 gateway / machine are separate connection and session-routing layers

- `internal/gateway` owns machine registration, heartbeats, capacity admission, session affinity, and the data-connection pool. It must not host plugin execution semantics.
- `internal/machine` owns machine-side registration, inbound data connections, and return-path routing. Workflows remain owned by `engine`.
- `engine` must not know that Gateway exists, and forwarding/routing logic must not leak into `engine` or plugins.
- Gateway and Remote Plugin are experimental. Their APIs and protocols may break without notice; call out compatibility impact explicitly when changing them.

### 3.5 Remote Plugins are a cross-language contract boundary

- `internal/remote` + `api/plugin/v1` + `sdks/remote_plugin/{python,nodejs}` form a single contract. A proto change must be mirrored in the Go client, the Python SDK, the Node.js SDK, and the examples.
- Remote Plugins currently support `Signal` and `Payload` only. Do not assume they can carry `Audio` / `Video` streams.
- `internal/remote` owns instance lifecycle, calls, and connection management. Plugin implementations must not build a second connection layer.

## 4. Engineering principles

### 4.1 Real-time correctness comes first

The following outrank "cleaner-looking" code:

- interruption takes effect promptly
- streaming output never stalls
- backpressure behavior is explicit
- a slow node cannot take down the pipeline
- buffer reuse is preserved
- session lifecycle stays under control

If a refactor makes cancellation timing, queue behavior, or memory ownership less obvious, drop the refactor.

### 4.2 Fewer layers, stronger boundaries

- `biz/handler` does not need a conventional layered architecture.
- "No layering" does not mean "no boundaries."
- Real-time state machines, runtime scheduling, schema semantics, and plugin registration must not leak into handlers.

### 4.3 Abstract only from repetition and stable semantics

- Do not abstract ahead of need.
- Once the same logic appears in two or more plugins or modules with stable semantics, consider a shared layer.
- Name abstractions after what they do. Avoid vague names such as `manager`, `helper`, or `util2`.

### 4.4 Prefer incremental, compatible change

- Favor changes that can land incrementally.
- For large refactors, introduce an intermediate layer first, then migrate callers.
- Do not change the runtime, the plugin protocol, and the workflow format in the same pass unless there is a clear reason.

## 5. Go conventions

### 5.1 Style

- Keep code simple, direct, and readable.
- Prefer explicit control flow over clever constructs.
- Expose the minimum necessary package API.
- `context.Context` is always the first parameter.
- For struct-scoped lifecycles, `context.Context` may be stored as a struct field.
- Return errors; do not swallow them. Keep logging and error returns distinct.
- Keep local names short but meaningful; avoid opaque abbreviations.

### 5.2 Package design

- A package should do one thing.
- Avoid import cycles.
- Logic shared by plugins but meaningful only to the plugin domain belongs in `internal/plugins/base`.
- Only generic utilities with weak business coupling belong in `pkg`.

### 5.3 Concurrency and lifecycle

- Treat changes to `internal/engine` and `internal/schema` as high risk by default.
- Every new goroutine must define: exit condition, `ctx` cancellation path, data ownership, and whether `Retain` / `Release` is required.
- Plugins wrapped in `MultiTrackPlugin` must assume that different `OnXXX` callbacks may run concurrently.
- Session lifecycle is fixed: `Acquire()` on connect (exactly one active connection per session) → `Pause()` instead of `Stop()` on disconnect → `Resume()` on reconnect → `Stop()` only after idle `Cleanup()` or an explicit `RemoveSession()`. Do not bypass this arbitration in the realtime layer. See `docs/reference/protocol.md`.
- Gateway / Machine follow the same "retain on disconnect, reclaim on timeout" rule. When changing the connection pool, heartbeats, or capacity admission, verify that capacity is not oversold and SessionKey bindings are not lost.

### 5.4 Logging and errors

- Logs should help diagnose real-time failures. Avoid duplicate or low-value output.
- Hot paths must not emit noisy logs.
- Error messages should state the action, the object, and the cause.

## 6. schema and memory model

`schema` is not a plain DTO layer. Everyone working in this repository must understand these rules:

- `Payload` / `Audio` / `Video` received in a callback are read-only by default.
- To modify data, obtain a writable copy via `Mutable()`.
- Call `ReadOnly()` before sending; do not mutate afterwards.
- Media objects you create for sending must still be `Release()`d by the creator after `Send`.
- If you hold a received media object asynchronously, `Retain()` it and `Release()` it when done.
- Do not blindly copy audio or video bytes into new large slices unless strictly necessary.

Any change to `audio.go`, `video.go`, or `payload.go` must add or update tests covering read-only enforcement, reference counting, buffer reuse, and concurrency safety. See `docs/guides/plugin.md` for the full model and examples.

## 7. engine invariants

- Before changing `engine`, answer: does this alter scheduling order, cancellation propagation, buffering/drop policy, session lifecycle, plugin metadata validation, or workflow assembly?
- **In worker-pool mode, nodes assigned to the same worker share execution time.** Any plugin with blocking work must be wrapped in `NewMultiTrackPlugin` to run on an async track.
- **Changing queue capacity or priority changes real-time semantics.** Justify it in the change description.
- Any new buffer must specify: capacity, behavior when full, release of residual data after cancellation, and whether dropped objects are `Release()`d.
- Never put slow operations on a synchronous path. Backpressure must be explicit; do not rely on implicit blocking.
- Modes, parameters, and lifecycle details live in `docs/guides/workflow.md`. Do not duplicate them here.

## 8. Plugin development

### 8.1 Ground rules

- One package per plugin, named after the plugin.
- Register through `engine.RegisterPlugin`. Declare input/output/port contracts in `PluginMetadata`; they participate in `BuildGraph` edge-contract validation.
- After adding a plugin, run `make generate` to regenerate `internal/plugins/init_gen.go`. Do not edit generated files, and do not add manual blank imports to `init.go`.
- Remote plugins register through the `internal/remote` namespace. Do not mix them with local registration.
- See `docs/guides/plugin.md` for interfaces, lifecycle, and runnable examples.

### 8.2 Responsibilities

- Plugins handle integration, protocol adaptation, and local state.
- Do not hard-code workflow orchestration inside a plugin.
- Reuse existing `schema`, `engine`, and `base` capabilities instead of building a parallel concurrency, buffering, or signaling stack.

### 8.3 Shared plugin layer

- Only stable logic shared by multiple plugins belongs in `internal/plugins/base`.
- `base` holds reusable components, not a grab bag.
- If a shared component ends up owning buffering, protocol events, and format conversion at once, split it.

### 8.4 Network and streaming plugins

- Handle `io.EOF`, `context.Canceled`, upstream interruption, and non-2xx responses explicitly.
- Streaming readers must handle chunk boundaries; never assume a single `Read` aligns with a frame.
- Audio conversion, resampling, and framing logic shared across plugins should be extracted into a standalone component rather than buried inside a provider.

## 9. HTTP, realtime, and protocols

### 9.1 Handlers

- Keep handlers direct. Do not add pass-through service layers for the sake of layering.
- Focus on parsing, validation, calling runtime/config capabilities, and returning responses. Do not hold complex runtime state.

### 9.2 Realtime

- More complex control flow is acceptable here, but it must stay within the real-time interaction itself.
- WebSocket and gRPC must share the same semantics: `Acquire` on connect, `Pause` on disconnect, `Resume` on reconnect, idle cleanup by `SessionManager`.
- When adding a packet type or changing the wire format, update `internal/protocol`, the web UI / TUI, and `docs/reference/protocol.md` together.

### 9.3 protocol / api

- External protocols are compatibility boundaries.
- Before changing fields, event types, or transport formats, assess the impact on clients, the TUI, the workflow editor, and existing workflows.

## 10. Web UI and Rust client

### 10.1 `clients/web`

- Stack: React + TypeScript + Vite; reactflow for the canvas, @rjsf for forms, zustand for state.
- Configuration forms and node metadata must be derived from the backend-exported schema and plugin metadata. Do not hand-write a copy that will drift.
- Do not duplicate backend runtime semantics in the frontend.

### 10.2 `clients/voce-tui`

- Optimize for stability, low overhead, and observability.
- The terminal experience serves debugging and demos; avoid unnecessary interaction complexity.

## 11. Configuration and documentation

### 11.1 Configuration

- Config structs and YAML loading live in `config`. Runtime resource cleanup belongs to the owning module.
- `configs/` holds local run inputs and is not committed. Committable examples live in `examples/*.yaml.example`.
- Workflows can be stored on disk (`workflow_dir`) or in Redis (`workflow_store`).
- A new config option must come with: a default, backward-compatibility analysis, documentation, and an example update.

### 11.2 Documentation

- Directory layout, index, and maintenance rules are defined in `docs/README.md`. Update the index and all links when adding, moving, or renaming documents.
- Design documents live in `docs/designs/<NN-topic>/design.md`; follow `.agents/skills/write-design-doc/SKILL.md`.
- Benchmark data goes to `docs/reports/` with a month-stamped filename. Never overwrite old results.
- Update the docs when any of the following changes: plugin integration, protocols, workflow/scheduling, Gateway / Remote Plugin / observability / benchmark behavior, or core runtime constraints.

## 12. Testing

Follow `.agents/skills/test-conventions/SKILL.md` by default. In addition:

- Test plugins with `PluginTester`, covering success, interruption, error, stream completion, and boundary inputs.
- Run `-race` for packages affected by changes to `internal/engine`, `internal/schema`, `internal/gateway`, or `internal/machine`.
- Hot-path changes (protocol codec, Scheduler / Node input, schema pools, pool Bind / Unbind, audio resampling) require a benchmark and a report of `ns/op`, `B/op`, and `allocs/op`.
- Realtime-path changes must verify at minimum: context cancellation, residual buffer cleanup, start/end signals, and audio/video frame forwarding.
- Build prerequisites: CGO and FFmpeg dev libraries; `libs/ten-vad` fetched by `make deps`; `clients/web/dist` built before `go build` (embedded via `go:embed`).
- Commands: `make test-backend` / `test-gateway` / `test-tui`; see `make help` for the full list.

## 13. Pre-submit checklist

- Does this break engine cancellation or scheduling semantics?
- Does this misuse schema read-only/mutable state or reference counting?
- Does this break Gateway / Machine capacity admission, session affinity, or retain-on-disconnect behavior?
- Did I keep the Remote Plugin contract in sync across Go / Python / Node.js?
- Did I put logic in the business or plugin layer that belongs in `engine`?
- Did I over-abstract plugin-specific logic into a global layer?
- Did I update the relevant tests and documentation?
- Is the configuration still consistent with the frontend form schema?

## 14. Anti-patterns

- Adding empty directories and pass-through interfaces for the appearance of layering
- Unnecessary allocations and byte copies on hot paths
- Spawning goroutines inside plugins without cancellation and release handling
- Spreading runtime control logic into handlers, clients, or config loading
- Putting single-purpose utilities in `pkg`
- Working around schema/engine constraints with one-off patches

## 15. Maintaining this file

If this file no longer matches the project, update it rather than letting outdated rules drive development.

This is a working agreement, not a historical record. Any deviation needs a clear justification and a corresponding documentation update.

This file contains constraints, priorities, and prohibitions only. Implementation details, configuration parameters, and procedures belong in `docs/`; do not duplicate them here.
